内部汇报材料01
01 · 现状

今天这件事有多重

门槛在工具，不在业务

要装开发工具、配连接、输指令，现场人员无法自助；每一次建档都要懂行的人陪着操作。

动作散在多个环节

取模板、填表、校验、建档案、存参数、核对结果，靠人在几个界面之间来回搬数据， 出错只能逐条重查。

结果不好追溯

改了什么、谁批准的、成没成功，散在聊天记录和个人电脑里，事后难以还原。

服务端能力其实已经齐了 缺的只是一个"普通人能用"的入口

02 · 目标

做成之后，同一条路变成这样

现在

装开发工具 → 配连接参数 → 输指令 → 人工逐步操作 → 人工核对结果 参与人：懂工具的人 耗时：每次都要人盯全程

之后

打开网页 → 登录 → 说一句话 → 系统执行并逐项请示 → 结果与凭证可下载 参与人：现场人员，手机即可 耗时：人只在决策点出现

三个真实使用场景

  • 取最新建档模板 —— 一句话拿到当期标准模板文件
  • 批量建档与参数保存 —— 上传填好的表，系统给计划，人确认后执行并回读
  • 协议转换作业 —— 交文档，系统出配置、校验、报告与交付包（第三阶段）

不改变任何既有工作方式

原有开发工具接入路径、服务端接口与全部作业能力保持不变； 网页只是新增一种用法。

关键设计：确认权在服务端

"我已确认"这句话不由机器自己说。页面上点下确认按钮时，服务端针对这一份计划发一张 一次性凭证，写入动作必须带这张凭证才执行；凭证过期、复用或校验服务不可用，一律拒绝。

结果一定带"没做什么"

每次执行都产出阶段报告与未执行清单；失败项不猜测成功，回执未知的标记为"未确认"。

计划字段与阶段划分沿用现有服务的真实返回结构。

04 · 方案怎么做

三句话讲清架构

① 复用，不重写

作业规范、校验规则、建档引擎、平台对接全部沿用现有 服务端与规范文件，网页只是新入口。

② 一人一条通道

每个登录会话有独立的执行环境与独立凭证， 避免不同人互相顶掉身份与数据归属。

③ 人只在决策点出现

中间过程实时可见，写入必须人确认； 确认权由服务端凭证承载。

05 · 投入判断

为什么这件事比看上去便宜

看起来要新建的东西实际情况（已存在）
网页后端的登录、鉴权、文件上传、结果下载 现有服务已提供 10 条非 MCP 端点（3 个页面 + 7 个 API），含带凭证的表格上传与模板下载，范式可直接沿用
建档的全部业务动作 已封装为 71 个可调用能力（查询 / 建档 / 挂载 / 参数 / 报告 / 协议管理）
让机器按公司规范干活 已积累 9 套作业规范文件（入口路由、字段映射、校验、打包），可直接喂给运行时
写入前的"人确认"机制 已有计划 + 确认两段式门禁，本次只是把"确认"从对话文本升级为服务端凭证
确认页面上要展示什么 现有返回已含可执行标志、冲突、阻塞项、逐项参数差异、批次，无需新增字段
谁做了什么、成没成 已有写操作留痕与阶段报告存储机制，按使用者分区可回看

真正要新写的三块

  • 网页界面与消息推送
  • 后端会话与凭证管理、执行环境调度
  • 权限与数据归属的加固改造（涉及既有凭证分配规则调整，属规格级变更）

第三阶段不是白送

协议转换中的"跑校验、出报告、打交付包"目前在规范里标记为待补的服务端能力， 需要补齐 6 项能力并同步升级作业规范，因此排在第三阶段。

06 · 交付节奏

三期交付，每期都有能用的东西

第 0 步先清理，再验证

先做两件不改业务代码的清理：改动前文件级快照（不建 git 基线，但必须有回滚点）与 技能目录只读治理（中间产物现写进技能目录，须改落会话工作区）； 再用 1~2 天确认：能否连上自家服务、中途能否请示、失败能否恢复。

第一期能查、能取模板

登录准入 + 网页对话 + 实时过程展示；查询、字典、模板生成与下载全链路可用。 这是最快能给人用的版本。

第二期能建档

上传已填表 → 计划卡片 → 确认 → 写入 → 回读 → 阶段报告；权限凭证与留痕闭环。 这是价值最大的一期。

第三期能转换协议

补齐 6 项服务端执行能力并升级作业规范后，交文档出配置、校验、报告与交付包可在网页完成； 同时让开发工具端也受益（不再依赖个人电脑环境）。

每一期的验收口径

  • 第一期：一句话拿到当期模板并能下载
  • 第二期：不点确认就写不进去；确认后结果与报告可核对
  • 第三期：交一份文档能拿到可交付包与测试报告

工期在第 0 步验证后给出；现在给数字是不负责任的。

07 · 安全与管控

四道闸门，讲清楚谁能干什么

问题怎么控制
谁能进门？手机号 + 验证码登录，并且必须在准入名单内；名单缺失时一律拒绝
进门能干什么？接入凭证只授予"能调用能力"，不代表可写平台； 云端写入仍需业务账号命中超级账号配置
谁批准动手？写入动作必须带服务端一次性凭证；机器自己声称"已确认"无效， 校验不通就拒绝（不做默认放行）
机器会不会乱来？第一期关闭命令执行能力，读写限制在本次会话的独立工作区； 服务代码、规范源目录、凭据文件一律拒绝访问
事后怎么查？按使用者留痕与阶段报告；拦截行为也留痕，可复盘

需要领导知情的两条前提

  • 对话与文档内容会经由外部智能体服务处理（需求方已确认可接受）； 含凭据的建档表格只在内部处理，且保留期短于一般文件
  • 新入口与现有服务同机部署，隔离依赖权限规则与工作区限制，不依赖物理分离； 若要更严，可后续改为独立主机或容器，不影响其它设计

用量控制

  • 每人每日对话次数上限（默认 100，可调）
  • 同时运行数量上限（默认 4，超限明确提示繁忙）
  • 单轮步骤上限，防止无限循环
  • 文件与产物按类别保留 30 天，含凭据文件 7 天

08 · 风险与前提

我不承诺没验证的事

事项状态不成立时的退路
外部运行时可被我们的后端驱动，并连回自家服务待验证 改为自研执行循环，工作量与规范复用度重估
执行中途能把"要不要写入"交回页面请示待验证 确认机制改在服务端改造，方案形态调整
会话可恢复（空闲回收后再唤起不丢上下文）待验证 提高并发预留，或缩短空闲回收
外部智能体账号用于多人服务的授权与额度口径需商务确认 收敛为内部少量人使用，或改用可控模型通道
手机拍照的协议文档识别质量待实测 第一期只收文本与电子表格，照片推后
现场"隔天继续上次任务"的能力待核实 明确限定为重新规划，进度以报告为准

已知的业务边界（不是本次引入，方案里不掩盖）

设备下发与监测点召测因现场通信契约尚未完全核实， 当前状态为受限：网页版不会绕过该限制，也不会把未确认的结果报成成功。 建档、参数保存、回读与报告不受此项影响。

09 · 需要的支持

还需要三件事（名单与账号已到位）

1 · 对外形态与 HTTPS 证书

一期直接公网：需定域名或 IP:端口、证书由哪里签发、用哪个代理组件， 并要求代理层关闭流式缓冲。该项未定不得进入部署配置。

2 · 账号额度的使用口径

智能体账号已确定（含免费模型档位），但用它支撑多人对外服务的额度与并发上限 需实测并作商务确认；这直接决定能开多少人。

3 · 一次现场验证机会

技术确认 + 一期试用需要一台目标环境做一次真实建档，验收口径见第 8 页。

结论

做成之后的样子

对人

现场人员手机上说一句话就能取模板、建档、查结果；懂工具的人从"每次陪做" 变成"只看异常"。

对事

批量建档从人工逐台操作变成一次规划、一次确认、逐项回读；没做的部分必须说明。

对管理

谁进门、谁批准、做了什么、结果如何，全部留痕可复盘，包括被拦下的动作。

一句话概括方案

现有服务不动，作业规范不动；新增一个网页入口与一层会话管控， 由智能体运行时替人干活，人只在写入前点一次确认。

下一步：第 0 步技术确认（1~2 天） 确认通过即启动第一期
