## 2. 关键设计约定（已对齐）

- 角色：后端沿用 `role="super"`/`"user"`（对外称 system/user）；role 判据＝**内置账号 + superAccounts 双源**。
- **内置 super 凭据**：`permissions.json` 的 `systemAccount`（实测 `13912986342 / 9413`，用户提供；本地敏感，不落源码）。
- **重启保持**：所有已签发 token（含本机）与内置凭据均持久化，重启后继续有效（§5 时序 A/R）。
- 云端写权限＝工具层 `_require_super()` 按 session.role 把关；平台调用凭据层独立（§3）。

---

## 3. 三套鉴权边界（基线）

| 链路 | 凭据 | 用途 | 边界 |
|------|------|------|------|
| 用户→server | MCP Bearer Token | 调用 /mcp、推导建档 owner | 只决定"能否连上"，不授云端写权 |
| server→平台 | system token（内置） | 调用平台 API；40100 自动刷新→降级 | 与 MCP Token 无关 |
| server→设备 | Excel 明文（edge_base_url/login/password） | EdgeDeviceClient RSA 建档 | 与云/MCP 完全独立 |

> 平台**凭据层**（用什么 token 调）与**权限层**（工具可否写）分离：
> `_call_platform` 优先共享 system token，失效 `arefresh` 内置，再降级到**当前请求自己**的 `fallback_token`；写工具进 `_require_super` 按 session.role 拦普通 user。

## 4. 代码改动点

### 4.1 `mcp_server/server.py` :: `TokenManager`
**目标（需求⑥）：本机 token 也持久化，重启后仍可用。**
- 改 `get_or_create_token(self, ip)`：对**任意 IP（含本机）**，先查 `self.ip_tokens[ip]`（未撤销）→ 复用；否则新 token＝本机且 `admin_token` 时用 `admin_token`、否则生成 `metam_pat_<hex>`，并**写入并持久化 registry**（`source` 标 `admin`/`auto`）。重启后 `is_valid` 认 registry 未撤销项 → 手头 token 有效。
- `is_valid` 保持：admin_token 精确匹配 或 registry 未撤销 user token。
- 作用：接入手头 token 与 .env 是否一致无关，重启后仍能连。

### 4.2 `mcp_server/token_manager.py` :: `SystemTokenManager`
- 增只读属性 `phone`（返回内置 `_phone`），供 role 判据比对。

### 4.3 `mcp_server/server.py` :: login role 双源（需求②④⑥之一）
- helper：
  ```python
  def _is_system_login(phoneNum: str) -> bool:
      if phoneNum and phoneNum == system_token_mgr.phone:
          return True
      return super_account_config.is_super({"phone": phoneNum})
  ```
- `login`：`is_system=_is_system_login(phoneNum)`；`role="super" if is_system else "user"`；message：super→「已授权，系统账号」，user→「已登录，只读权限」；super 且系统 token 失效 → 沿用 `aupdate_credentials(phoneNum,code)`（=需求④、⑦持久化）。

### 4.4 明确不改
`init` / `refresh` / `update_credentials` / `_call_platform` / `_try_fallback_and_report` / `_require_session` / `_require_super` / TokenManager 其余 / edge 全链路。

### 4.5 测试 `mcp_server/tests/`
- 更新 login role 旧断言。
- 新增：双源判定单测；**并发回归**（两会话 system 失效各自 fallback 独立）；**重启持久化**单测（本机 token 写入 registry→重新 load→is_valid 仍真；内置凭据持久化后 update 反映到 permissions.json）。

## 5. 关键数据时序

### A. 启动
```
server 启动
 ├─ TokenManager 加载 .token_registry.json（所有 token 含本机）
 └─ system_token_mgr.init() 读 permissions.json:systemAccount -> login -> system token
      ├─ 成功：日志"系统 Token 获取成功"（可读写）
      └─ 失败：仅告警，继续启动
```

### R. 重启后 token 复用（需求⑥⑦）
```
重启前：本机用户访问，token=T0 已写入 .token_registry.json；内置凭据已写入 permissions.json
重启后：
 ├─ TokenManager 加载 registry：T0 未撤销 -> is_valid(T0)=true -> 用户 token 仍可用
 └─ init 用 permissions.json 内置凭据再次登录 -> system token 恢复可用
```

### B. 用户登录 role 判定
```
login(phone, code) -> role=_is_system_login(phone) ? super : user
 ├─ super -> 系统 token 失效则 aupdate_credentials(phone,code)（更新+持久化内置）
 ├─ user  -> fallback_token=本人业务 token（只读托底）
 └─ 写 session(mcp_token -> {role, fallback_token})
```

### C. 只读请求（内置正常）
```
get_xx() -> _require_session -> _call_platform 用 system token 调平台 -> 成功
```

### D. 只读请求（内置失效·多用户并发，需求⑤）
```
系统A(user)                    系统B(user)
 ├─ system token 无效            ├─ system token 无效
 ├─ arefresh(内置) 失败           ├─ arefresh(内置) 失败
 └─ 用 A 的 fallback_token 读    └─ 用 B 的 fallback_token 读
    （A 能看的数据）                （B 能看的数据）
互不影响：fallback_token 是本会话语义，各自独立。
```

### E. 内置失效恢复（需求④/⑦）
```
内置号 login(1391…, 9413) -> role=super -> aupdate_credentials -> 
更新并持久化 permissions.json systemAccount -> system token 恢复，全体回到共享可用
```

## 8. 风险 / 边界
- 无内置配置：无任何 super，全 user 只读，需人工配 permissions.json 激活。
- 普通 user 只读依赖本人 `login` 过（才有 fallback）。
- **system 账号本人失效无法读**：super 登录者不存 fallback；若内置账号本身也失效则该 super 会话只读不了（重 login 可恢复，见时序 E）——接受。
- 明文持久化：内置 code 存 permissions.json、MCP token 存 .token_registry.json（均已 gitignore/本地敏感）。沿用现状，加密存储单列后续项。
- 并发：单进程 asyncio，SessionRegistry 内存、按 mcp_token 隔离、无锁；system token 单例只由内置维护，普通 user 不写 → 并发安全。
