## Context

当前 `excel_reader._parse_topology` 使用两个独立集合 `gw_seen` 和 `mon_seen` 分别跟踪网关和监测点。当设备同时出现在两种角色时（如子网关兼挂载点），会创建重复节点。`node_map()` 采用后写覆盖策略，导致计划和执行阶段取到不同对象，父关系丢失。

参见 proposal.md - Why。

## Goals / Non-Goals

**Goals:**
- 确保每个设备名称在拓扑中只对应一个节点对象
- 保留首次建立的父关系，不因后续角色变化而清空
- 检测并报告真正的多父冲突（同一设备在不同挂载点块下作为监测点出现）
- 在回读验证中区分"模板根节点"与"父ID尚未解析"，防止误判
- 保持现有功能不变：模板列序、端口下拉、品牌型号转换、UPDATE/SKIP逻辑

**Non-Goals:**
- 不改变模板结构或列顺序
- 不新增设备类型或字段
- 不修改已建设备的处理方式（UPDATE/SKIP仍保持现有行为）
- 不实现存量子网关的自动迁移（AI_test3等已错误挂载的设备需独立处理）
- 不改变挂载后参数保存的触发条件

## Decisions

### 决策1：使用统一名称索引替代双集合

**选择**：在 `_parse_topology` 中使用 `name_to_node: dict[str, TopologyNode]` 替代 `gw_seen` 和 `mon_seen`。

**理由**：
- 单一索引确保名称全局唯一，避免重复创建
- 简化逻辑：无需分别检查网关和监测点集合
- 便于查找和更新已有节点

**备选方案**：
- 保留双集合但在创建前交叉检查：逻辑更复杂，容易遗漏边界情况
- 在 `topological_order` 中去重：太晚，解析阶段已产生错误

### 决策2：保留首次父关系，检测真正冲突

**选择**：
- 节点首次创建时设置 `parent_key`（可能为空）
- 后续出现时复用已有节点，不修改 `parent_key`
- 仅当同一设备在**不同挂载点块下作为监测点**出现时，才报告多父冲突

**理由**：
- 子网关先作为挂载点出现（有父），后作为挂载点管理下级设备（无新父），不应视为冲突
- 真正的冲突是同一设备在不同网关下都作为监测点出现（物理上不可能）
- 合并单元格的续行不应触发冲突检测

**备选方案**：
- 任何父关系变化都报错：过于严格，会误报合法的子网关场景
- 允许后写覆盖父关系：回到原始bug

### 决策3：排序前增加唯一性断言

**选择**：在 `build_plan` 调用 `topological_order` 前，检查 `template.nodes` 中是否有重复的 `node_key`。

**理由**：
- 作为安全网，防止解析器的bug漏网
- 提供清晰的错误信息，而非在排序中静默丢节点
- 不改变 `topological_order` 本身的逻辑

**备选方案**：
- 在 `topological_order` 内部检查：会改变该函数的职责
- 依赖解析器保证唯一：缺少防御性检查

### 决策4：回读验证区分根节点与未解析父ID

**选择**：在 `_readback_verify_device` 中：
```python
if item.get("action") == "create" and node.parent_key:
    expected_parent = session.key_to_device_id.get(node.parent_key, "")
    if not expected_parent:
        # 父ID尚未解析，不能视为根节点
        mismatches.append("parentId: 父设备ID尚未解析，禁止验证")
        return False, mismatches
```

**理由**：
- 模板根节点（`node.parent_key` 为空）允许与后端 `-1` 等价
- 有父键但父ID未解析时，不能降级为根节点验证
- 防止"未挂载却报告成功"的误判

**备选方案**：
- 保持现有逻辑，依赖后续挂载修正：无法阻止错误的成功报告
- 要求父ID必须已解析才能进入验证：过于严格，可能阻塞合法流程

### 决策5：测试策略

**选择**：
- 新增测试类 `TestSubGatewayMount` 或在 `test_archiving_template.py` 中扩展
- 覆盖场景：本例正/反序、合并续行、多父冲突、环检测、CREATE父ID晚绑定、回读错根拒绝
- 使用真实生成的工作簿，不手工构造节点

**理由**：
- 现有测试漏检原因：包含子网关的用例绕过了解析器
- 必须从Excel解析开始，确保完整链路
- 行序变化测试确保修复不依赖特定顺序

**备选方案**：
- 仅添加单元测试：无法验证集成行为
- 使用手工构造节点：绕过真实解析逻辑

## Risks / Trade-offs

**风险1**：多父冲突检测可能过于严格  
→ **缓解**：仅在"同一设备在不同挂载点块下作为监测点出现"时报错，子网关场景不触发

**风险2**：现有测试可能依赖旧的重复节点行为  
→ **缓解**：运行全量测试套件，必要时调整测试夹具（不修改生产代码适配测试）

**风险3**：父ID未解析时拒绝验证可能阻塞合法流程  
→ **缓解**：仅在CREATE动作且有父键时检查；UPDATE/SKIP不受影响；父ID晚绑定是正常现象，但验证时必须已解析

**风险4**：存量子网关（如AI_test3）无法自动修复  
→ **缓解**：明确文档说明本次修复仅防止新问题；存量迁移需独立确认和执行

**权衡**：选择保守修复策略，不引入新功能（如子网关参数自动保存），降低回归风险
