约束：现有 IDE 接入路径与 `/mcp` 工具行为不变；新后端与 MCP Server 同机但独立进程、独立 venv；

需求方不提供 git 基线提交，回滚点改用 D17 的文件级快照。

## Goals / Non-Goals

**Goals:**

- 让同一份 SKILL.md 大脑同时服务 IDE 与 Web，避免为 Web 重写一套业务能力造成实现漂移。
- 在"每个用户会话"粒度上隔离运行时、接入凭据、工作区与业务归属，杜绝跨用户身份串号。
- 使写入类操作的用户确认成为服务端可验证事实，而非模型自述。
- 让会话可跨连接、跨设备续用（移动端锁屏/切后台不失联）。

**Non-Goals:**

- 不在本变更内实现协议转换的执行类服务端工具与对应 SKILL.md 改写（另立变更，见 D8）。
- 不改造 MCP 工具入参/返回语义，不新增业务工具。
- 不引入容器化/K8s 部署，不做多机分布式会话调度。
- 不追求实时双向语音/视频类交互，不做富协作编辑。

## Decisions

### D1 四层职责切分，后端独立成进程

已定基线：后端顶层目录为 `webchat/`（与 `mcp_server/` 平级），独立 venv，监听 `127.0.0.1:8800`，
仅由反向代理对外暴露；MCP Server 继续用 `MCP_PORT`（默认 8765）。后端调工具走 `http://127.0.0.1:<MCP_PORT>/mcp`。

```
+----------------+   HTTP/SSE   +--------------------+  SDK  +---------------+
| Web 前端       | ------------> | 后端 (Host 层)     | ----> | CLI 运行时    |
| 交互/决策      | <------------ | 会话·凭据·门禁·池  | <---- | 模型循环·技能 |
+----------------+   事件流      +---------+----------+       +------+--------+
                                          | HTTP 回环 /mcp (Bearer) | MCP Client
                                          v                         v
                              +----------------------------------------+
                              | MCP Server（工具层，行为不变）           |
                              +----------------------------------------+
```

- 为什么不在 `CompositeApp` 内长出对话层：MCP Server 的职责是工具与鉴权，一旦持有对话状态、
  进程池与模型编排，`/mcp` 的稳定性与"现有功能不变"承诺会被牵连；且 `mcp_server` 与后端依赖
  集不同（SDK + OCR 库体积大），混在一个 venv 会放大升级冲突面。
- 备选（已否决）：① 同进程旁挂 chat 包 —— 依赖耦合、重启半径大；② MCP Server 反向驱动模型 ——
  与工具层定位颠倒，且需要为公网暴露额外的模型编排职责。

### D2 运行时用 Qoder Agent SDK，不手搓 stream-json，也不裸连模型 API

- 选 SDK：官方开放 Python 包、内置兼容 CLI 运行时，事件流、多轮输入、审批回调、Hooks、会话
  恢复/派生、轮次上限均为现成能力，可避免自研 stream-json 状态机与其私有事件格式的长期维护。
- 否决裸连模型 API：需在服务端重建 agent 循环 + 文件与执行能力 + Skills 加载，等价于把 L3 能力
  全部改造成服务端工具（我早先方案），会造成 IDE 与 Web 两套实现并存、行为漂移。
- 否决 headless `-p`：官方明确纯 headless 下需确认动作自动拒绝，无法满足"中途把决策交给网页用户"。
- 纪律：SDK 的类型只允许出现在后端 `adapters/` 内单个适配层；业务层只认 D9 的自有事件契约。
  这是"将来可切换其它运行时"的真正保障点，而不是命令模板抽象。

### D3 会话 : 实例 : 接入凭据 = 1 : 1 : 1

凭据在 CLI 进程启动时随 MCP 配置绑定，运行期不可切换；旁观者不额外起实例。备选"一实例轮转服务多用户"
被否决：会把两个用户的上下文与工作区混在一起，并使业务归属判定失真。实例池采用"活跃持有 + 空闲回收 +
按需恢复"，恢复能力以 V2 验证结果为准。

### D4 归属主体与接入凭据解耦

- Web 路径：`owner_id = SHA-256("webchat:" + 规范化手机号)`；手机号明文只出现在 mint 请求、
  准入配置与审计字段中，不作为文件名。规范化规则：去分隔符、保留国家码前缀的 E.164 形式。
- IDE 路径：保持 `owner_id = SHA-256(接入 Token)`，由凭据族别分支决定，不改既有产物归属。
- `SessionRegistry` 与产物归属在 Web 路径改用 `owner_id` 为键，`mcp_token` 降级为"本次调用的
  承载凭据"，用于审计族别标注。
- 备选：直接替换 `derive_owner_id` 为语义化 id —— 否决，会同时冲击文件名合法性校验、历史分区
  文件迁移与既有下载链接形态。

### D5 Token Registry v3：主键改为凭据

`entries` 以凭据为主键，来源地址、接入主体引用、凭据族别（`ide` / `session`）、有效期、撤销状态
降为属性。相应重写 `is_valid` / `revoke` / 最后访问时间更新，使其按凭据而非地址判定。
迁移沿用既有 `_backup_registry` 范式与 schema_version 检测，损坏时"备份 + 建空表 + 绝不授予 system"
的保守策略保持不变。备选"在 v2 上叠加一个会话表"被否决：两套事实源会长期分叉。

### D6 mint 端点用独立服务凭据，不复用 MCP_AUTH_TOKEN

`mcp-token-management` 已把"本机地址返回管理员 Token"写为既有语义，且管理员凭据同时被
`_get_api_token()` 用作系统级接入凭据；若复用它，铸票权与系统接入权将无法分离、也无法单独吊销
后端。新增 `WEBCHAT_MINT_SECRET`（高熵、可轮换）+ `WEBCHAT_ALLOWED_IPS`，铸票请求必须同时满足
两者；铸出的凭据一律 user 级并带 TTL 上限与速率限制。`WEBCHAT_MINT_SECRET` 与智能体账号凭据均
只存本地未跟踪配置（见 D6 末尾的凭据存放基线），不得出现在仓库或命令行中。准入手机号白名单另存
独立文件，不写入
`permissions.json`——后者是云端写权限事实源且会被 `SystemTokenManager` 读写回，不应与"谁能进门"
的变更频率混在一起。

### D7 写门禁：服务端一次性票据 + Fail-Closed

```
模型 -> 写入工具(confirm=true, plan_id=P)
          |
          v
   PreToolUse Hook (配置注入自工作区之外, agent 不可写)
          |  查后端: P 是否有未消费票据
          +-- 无/过期/不可达 -> deny  (fail-closed)
          +-- 有 -> allow, 票据立即作废
```

- 拦截范围仅限写入类工具集合（沿用既有 `WRITE_TOOLS` 语义与边缘写动作），只读/探测不要求票据，
  避免每次调用都多一次往返并扩大故障面。
- 否决"只依赖模型自填 confirm"：公网场景下模型可能被上传文档内容诱导自行置真。
- 否决"只靠地址参数解析限制 Bash 写路径"：命令是自由文本，变量拼接与相对路径无法穷举校验。

### D8 一期禁用命令执行能力，L3 执行另立变更

一期 Web 会话的能力白名单不含命令执行，读写仅限会话工作区 + 资源包只读母本。后果：协议转换中
"跑转换/测试脚本、打 ZIP"三步在 Web 一期不可用，必须由服务端工具承担——即
`test-validation/SKILL.md:188-193` 已规划并已声明"在沙箱中执行"的五个工具，外加打包工具。因这批
工具会改变交付给 IDE 客户端的资源包语义并触发资源包版本升级，独立成一个后续变更，本变更只在规格
中固化"执行必须走服务端工具"的约束。备选（极窄命令白名单）被否决：其可控性依赖对命令文本的解析，
不成立。

### D9 事件契约：自有 v1 事件 + seq + 游标重放

不直接用 SDK 事件形态，也不引入 WebSocket。事件类型固定为一组语义名（对话增量、工具调用、工具结果、
产物、计划就绪、请求补充、拦截、错误、收尾），统一带 `v`、`seq`、`chatSessionId`、`ts`。前端遇未知类型
降级展示而不中断。SSE 断线用 `Last-Event-ID` 续传，补历史用带游标的查询接口。选型理由：SSE 单向流足够、
与既有 `/api/*` 的 Bearer 鉴权范式一致、移动端重连语义清晰；备选 WebSocket 增加状态机与心跳成本。

### D10 单写者租约 + 只读旁观

会话持有一个执行者租约（默认 45s，前端 15s 心跳续约），后来者只读旁观，可显式接管（接管先中断当前执行
轮再转移）。备选"每标签页各开会话"会造成用户认知分叉与实例数按标签页膨胀，直接穿透全局实例上限。

### D11 产物交付：后端代理 + 一次性 grant，凭据不进 URL

既有 `/api/archive/templates/<id>?owner=<摘要>` 与 `/api/logs?token=` 把凭据或归属摘要放在地址查询串
（`server.py:2946` 明确"file_id 本身即为票据"），与"公网禁止 URL 传凭据"的规范冲突：新链路统一改为
请求头携带会话凭据与一次性 grant 的后端代理下载；同时给这两个既有端点加公网门控（公网形态拒绝 query
传凭据，内网形态保持既有行为，避免破坏现有客户端）。

### D12 会话数据双写自有存储，保留期沿用既有分类语义

qodercli 的持久会话目录只作为执行加速（省上下文重传、支持恢复），不作为事实源；会话列表与历史回看的
事实源是后端自有存储。保留期映射到 `cleanup.py` 的既有分类：`temp`（会话工作区）随会话销毁清理、
`result`/`template` 30 天（与 `DEFAULT_TTL_DAYS` 对齐）、含凭据的建档表格 7 天、`audit`（写操作日志）
维持现状不清理、未知分类一律保留。

### D13 OCR 在后端本地完成，做成可插拔 provider

图片识别不引入第二个外部数据目的地，也不要求模型视觉能力（CLI 因此只需读文本，能力面更小）。
上层只依赖 provider 接口，便于后续替换实现。上传入口优先级：文本粘贴 > 电子表格文件 > 屏幕截图 > 拍照；
识别失败或行列结构无法保留时必须显式提示，不得静默以猜测内容继续。

### D14 Skill 投放与版本

后端按当前服务器资源包（`agent_assets/skills/` + `package-manifest.json`）维护一份**共享只读母本**，
会话工作区内只放引用/入口，不逐会话解包（降低冷启动耗时与磁盘占用，并保证同一时刻所有 web 会话与 IDE
拿到同一版本）。Web 会话使用的 skill 版本跟随服务器资源包版本，不另立版本轴；母本目录对 agent 只读。

**该投放方式有一个前置条件：作业产物不得写入技能目录。** 现状相反（见 Context：本地副本技能目录内
已存在 113 个文件、11.0 MB 的作业中间产物），因此必须先按 D16 治理，否则并发会话会互相污染共享母本。

### D15 工具面按意图分组收敛

71 个工具的全量 schema 每轮约 1.5~2.5 万 token。后端按 `xlpa/SKILL.md` 意图路由表推导会话所需工具子集，
经运行时的工具白名单/允许服务器名等参数在会话启动时收敛；分组映射与实测节省量以 V4 结果校准。
备选"全量挂载"被否决：成本与误选工具概率都会随之上升，且随工具增长恶化。

### D16 技能目录只读与作业产物落位治理（一期前置）

共享母本只在"技能目录不可被作业过程写入"时成立。现状已成立的是分发源干净（`agent_assets/skills/`
无 temp/dist），不成立的是安装/运行副本（`.qoder/skills/modbus-conversion/temp/` 有 113 个文件、11.0 MB）。

- 治理要求：技能目录一律只读；文档转换、逐页抽取、中间图、生成的配置与分发包只能写会话工作区。
- 实施顺序：先清现有残留→在 SKILL.md 中把中间产物路径改为工作区变量→再加只读属性与 Hook 拦写。
- 不做会怎样：D14 的共享只读母本在公网并发下会被前一个会话写脏，后一个会话读到他人上传的协议文档。
- 备选（已否决）：每会话解一份独立副本——磁盘与冷启动成本随并发线性增长，且无法保证版本一致。

### D17 不做 git 基线，改用改动前的文件级快照

需求方明确**不做 git 基线提交**（仓内核心文件长期未跟踪，建基线会把大量无关改动一次性纳入
版本控制）。因此回滚点改用等效但粒度更粗的控制：

- 每项改动开始前，生成带时间戳的文件级快照，覆盖本次要改的 Python 模块与运行态文件
  （含 `.token_registry.json`），沿用仓内 `_backup_registry` 与 `skills_backup_{timestamp}` 范式。
- Registry v2→v3 迁移自身仍必须**先备份后写**，且启动时遇损坏继续执行既有的保守策略。
- 快照只用于逐文件恢复，不得把它当版本控制使用。

**残余风险（已告知需求方并接受）**：没有 diff、无法证明改动边界、不能逐提交回滚，
事故归因能力弱于 git 基线。若后续某刻建立了干净基线，本条替代控制即可废弃。

### D18 准入名单与写权限名单严格分离

将出现两份手机号名单：后端的 web 准入名单（“能不能进门”）与 `permissions.json` 的
`superAccounts` + 内置账号（“能不能写平台”）。两者语义不同、变更频率不同、变更人可能不同。

- 规则：**写权限的唯一判据是 `permissions.json` + 业务登录结果**；准入名单命中不产生任何写权限。
- 不得合并为一文件；不得把 `permissions.json` 当准入名单维护（它会被 `SystemTokenManager` 读写回）。
- 工具返回与会话开场说明必须表达该差异，沿用现有能力矩阵的措辞，避免维护者误解为一张表。
- 名单内容（手机号为 PII）**不得写入仓库内的任何文档或工件**；只存于本地未跟踪配置文件，
  仓内只给结构示例。首批名单由需求方线下提供（2 个号码）。

## Risks / Trade-offs

- [SDK 无法连自家 `/mcp`，或 canUseTool/Hook 拿不到含 `plan_id` 的完整参数] → 作为 tasks 的
  前置验证门槛；失败则回退为"后端自建工具循环 + L3 服务端工具化"路线，本变更的 D2/D4/D5/D12
  仍成立，仅 D2/D7/D8 需重写。
- [同机部署使 agent 与服务端密钥处于同一系统用户下] → 一期靠 D7 路径白名单 + D8 禁命令执行 +
  D14 母本只读替代物理隔离；若一期改为独立主机或容器，可撤掉部分补偿控制（记录在 Migration Plan）。
- [会话/实例/凭据 1:1 使资源开销随并发线性增长] → 全局实例上限 + 空闲回收 + 恢复能力兜底；
  超出即明确繁忙，不复用他人实例。
- [禁命令执行使 L3 一期不可用] → 已在 D8 明确为非目标，并给出后续变更路径；Web 一期价值集中在
  L1 查询与 L2 建档闭环。

## Migration Plan

1. 建回滚点（D17）：不做 git 提交；改为每项改动开始前生成带时间戳的文件级快照（涵盖待改
   模块与 `.token_registry.json`）。快照未生成不得动手改代码。
2. 技能目录治理（D16）：清理现有 temp 残留、改中间产物落位、加只读与拦写；完成后才能启用共享母本。
3. 前置验证（tasks 中 V 组）通过后才进入实现。
4. MCP Server 侧改动分两步上线，各自可独立回滚：
   - 第一步只做 Registry v2→v3 迁移与凭据族别扩展，不开放 mint 端点；重启后先验证 IDE 凭据
     与接入页行为不变。
   - 第二步开放 mint 端点（默认 `WEBCHAT_ALLOWED_IPS` 为空即拒绝所有），后端联调时再填白名单。
5. 后端与前端以独立发布单元部署：后端首次启动仅开准入与登录链路，运行时实例池上限先设 1，
   验证 1:1 隔离与门禁后再放量。
6. 回滚策略：从带时间戳的文件级快照逐文件恢复 + 还原 `.token_registry.json` 备份；后端可整体停用
   而不影响 IDE 接入（新增能力为附加式）。
7. 公网暴露前必须完成（**一期即需，不做内网过渡**）：HTTPS 反向代理（沿用
   `XLPA_PUBLIC_BASE_URL` 强制 HTTPS 的门控风格）、SSE 关缓冲、既有 query 传凭据端点的公网门控、
   准入名单非空、全局实例上限与配额生效。因不做内网过渡，4.1 与本节不得排在一期之后。
