# Karpathy 编码行为准则

> 源自 Andrej Karpathy 对 LLM 编码陷阱的观察，收敛为三条行为约束。
> 与另三份规范互补：那三份约束"代码怎么写"，本文件约束"动手前怎么想、
> 做到什么算完成"。
> 适用文件：所有代码改动（`.py` 为主）

---

## 0. 与既有规范的边界

以下约束已由其他规范覆盖，本文件**不重复表述**，也**不重新解释**：

| 已有约束 | 出处 |
|----------|------|
| 仅约束新增代码，存量代码不要求整改 | `pep8-coding-style.md` 前言 |
| 不改动无关代码，禁止重构核心逻辑，保留旧分支原样 | 现有功能保护与回归测试规范 |
| 分析需基于实际代码与文档核实，严禁臆测 | 分析任务事实规范 |

第 3 项「不改动无关代码」已完整覆盖原准则中的 Surgical Changes，
故本文件不再收录该条，仅保留以下三项未被覆盖的内容。

---

## 1. Think Before Coding — 先摆假设与权衡

**不做隐式假设，不掩饰困惑，主动摆出权衡。**

在开始实现之前：

- 把打算采用的假设**显式写出来**。假设未经确认即不确定时，提问，
  不要靠猜推进。
- 需求存在多种解读时，**把所有解读列出供选择**，不静默替对方选定一种。
- 存在更简单的方案时**说出来**，该反驳时反驳——默默按更复杂的做法走
  等于替对方做了个未经审视的决定。
- 卡住时**停下**。指明到底哪里不清楚，再提问；不要边写边猜。
- 发现的与任务正交的问题（规格自相矛盾、接口已废弃、前提不成立），
  **先上报**，不自行绕开或顺手改掉。

「基于事实、不臆测」约束的是结论的来源；本条约束的是**决策路径上的
显式化与提问时机**，两者不互相替代。

---

## 2. Simplicity First — 不引入未被请求的抽象

**用能解决问题的最少代码，不写任何试探性的东西。**

- 不写未被要求的功能。
- 不为只用一次的代码建抽象层。
- 不加未被要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景写错误处理。
- 写了 200 行而 50 行能解决，就重写。

自问：资深工程师会不会说这过度复杂？会 → 简化。

**适用边界（与现有功能保护规范对齐）**：本条只约束**本次新写的代码**。
不得以"简化"或"这段更臃肿"为理由重构存量核心逻辑或改变原有行为——
那是无关改动，由现有功能保护规范禁止。

**例外**：仓库既有约定（如 `pep8-coding-style.md` 的命名、docstring、
类型注解要求）属于**被要求的**内容，不视为过度设计。

---

## 3. Goal-Driven Execution — 交付前先给出可验证判据

**先定义成功判据，再循环到验证通过。**

把祈使式任务改写为可验证目标：

| 原始说法 | 改写为 |
|----------|--------|
| "加校验" | "先为非法输入写用例，再让它们通过" |
| "修这个 bug" | "先写一个能复现它的用例，再让它通过" |
| "重构 X" | "改动前后用例均全绿" |

多步骤任务先给一份简短计划，每步自带验证项：

```
1. [步骤] → verify: [检查项]
2. [步骤] → verify: [检查项]
3. [步骤] → verify: [检查项]
```

- 每步的 verify 必须是**可独立执行的检查**（一条命令、一个断言、
  一处可读的事实），不接受"确认没问题"这类主观判据。
- 宣告完成前，附上判据的**实际执行结果**。跑不过就说没跑过。
- 默认验收基线沿用仓库既有约定（现有 pytest 基线全绿、未破坏既有
  用例），本文件**不重复规定具体数字**，以免基线变化后规则失效。

强判据可以支撑独立循环到完成；弱判据（"能跑就行"）会不断回来要求澄清。

---

## 4. 力度权衡

本文件偏向**稳妥而非速度**。琐碎改动（改错别字、显然的一行修改）
不必走完整流程——目标是减少非平凡工作上的昂贵错误，不是拖慢简单任务。
